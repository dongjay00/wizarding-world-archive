# PRD — The Wizarding World Archive

> 제품이 **왜(WHY)** 필요한지. 사용자 문제, 목표, 검증 가능한 수용기준.
> spec이 WHY 초안을, requirement가 수용기준으로 조인다. Plan 게이트(`validate_prd`) 통과 시 freeze.
> architect가 WHAT/HOW를 만들 때 읽는 유일한 상위 입력.
>
> ⚠ 이 문서는 **완성된 앱에서 역복원**된 PRD다(retro-PRD). "왜 이렇게 만들어졌는가"를 사후 명문화한 것.

## WHY — 문제와 배경

해리 포터 세계관 데이터(PotterDB)는 원본 API로는 존재하지만, **탐색 친화적이고 아름다운 열람 경험**은 없다. 팬·방문자가 캐릭터·주문·마법약·영화·책을 한 곳에서 시각적으로 몰입해 둘러볼 표면이 필요하다.

부차적으로, 이 저장소는 **frontend team governance(하네스) 실험의 기준 앱**이기도 하다 — "이미 완성된 실앱에 거버넌스를 역으로 입혔을 때 성립하는가"를 검증하는 대상.

## 목표 (Goals)

- G-1. 5종 엔티티(Character·Spell·Potion·Movie·Book)를 **목록 + 상세**로 열람.
- G-2. 목록에서 **검색·필터·정렬·페이지네이션**으로 원하는 항목에 도달.
- G-3. 세계관 몰입을 주는 **비주얼**(하우스 색 정체성, 글래스모피즘, 마법 모션).
- G-4. 외부 API 지연·실패에 **무너지지 않는** 로딩/에러/빈 상태.

## 비목표 (Non-goals)

- 인증·사용자 계정, 즐겨찾기·댓글 등 사용자 생성 데이터.
- 쓰기 연산(canon 변경). 이 앱은 read-only(→ Domain R-1).
- 오프라인·PWA.
- _다국어(i18n)는 2026-07-10 활성 목표로 승격됨 → 아래 「다국어 i18n」 섹션. 단 API 가변 콘텐츠는 영문 원본 유지(번역 스코프 밖)._

## 대상 사용자

해리 포터 팬 / 캐주얼 방문자. 로그인 없이 즉시 탐색. 데스크톱·모바일 반응형.

## 수용기준 (검증 가능)

> requirement step이 조인 acceptance. review가 이 목록으로 수용 판정.

- **AC-1**: 5개 엔티티 각각 `/characters`, `/spells`, `/potions`, `/movies`, `/books` 목록 라우트와 `/{entity}/{id}` 상세 라우트가 존재하고 렌더된다.
- **AC-2**: 목록은 서버 페이지네이션을 사용하며(페이지 크기 기본 24), 페이지 이동 시 해당 페이지 데이터가 로드된다.
- **AC-3**: Characters 목록은 이름 검색(`name_cont`)과 House 필터(4하우스 + All)를 제공한다.
- **AC-4**: 데이터 로딩 중 로더, 실패 시 에러 메시지, 결과 0건 시 빈 상태 UI가 각각 표시된다(→ Domain R-3).
- **AC-5**: House를 가진 Character 카드는 해당 하우스 색 정체성을 반영한다(→ Domain R-4).
- **AC-6**: 이미지가 없는 항목도 깨지지 않고 대체 표현으로 렌더된다.
- **AC-7**: `tsc --noEmit`, `npm run lint`, `npm run build`가 모두 통과한다(→ Constraints C-1~C-3).

### 테마 토글 (D-2 재진입, 2026-07-09 · decision-queue D-2 option (a))

> spec가 아래 WHY를 향후 후보에서 활성 목표로 승격, requirement가 AC-8~10으로 조임. 근거: UIUX UX-1, ADR-0006(known defect), Architecture A-2.
> **WHY**: 다크/라이트 토글 어포던스가 설계됐으나 실제 색을 못 바꿔(사실상 다크 고정) 사용자 신뢰를 해친다 → 토글이 진짜로 동작하는 라이트/다크 전환을 제공한다.
> **스코프**: 기능적·정합적 라이트 테마(gate1 확정). 바스포크 라이트 리디자인은 비목표.

- **AC-8**: Header에 테마 토글 컨트롤이 있고, 클릭 시 라이트↔다크가 **실제 색으로** 전환된다(배경·전경·표면). 선택은 새로고침 후에도 유지된다(next-themes 지속성). → UX-1 해소.
- **AC-9**: 라이트/다크 **양쪽 모두**에서 본문 텍스트 대비가 읽힌다(WCAG AA 4.5:1 지향). 하드코딩 다크(`text-white`, `slate-950` 등)로 인해 라이트에서 깨지는 표면이 없다. 글래스 표면(`.glass`)이 두 테마에서 각각 가독.
- **AC-10** (기제 일원화): 테마 전환이 next-themes `.dark` 클래스 ↔ globals.css `.dark` 셀렉터로 단일화되고, `@media prefers-color-scheme` 이원화·ThemeProvider **이중 래핑**·빈 `themeStore.ts` 잔재가 제거된다.

### 필터 상태 소유 일원화 (D-1 재진입, 2026-07-09 · decision-queue D-1 option (a) 변형)

> spec가 아래 WHY를 향후 후보에서 활성 목표로 승격, requirement가 AC-11~13으로 조임. 근거: UIUX UX-2, Constraints C-S2, ADR-0003, decision-queue D-1.
> **WHY**: 필터 상태의 소유가 **이원화**돼 있다 — 설계는 `lib/stores/filterStore.ts`(전역 store)를 상정했으나, 실제 페이지는 각자 local `useState`로 필터를 든다. 그 결과 (1) store는 소비자 0의 **死코드**이자 "상태 이중화"(C-S2 위반) 리스크로 남고, (2) 필터 상태가 URL에 없어 **링크 공유·새로고침 시 필터·검색·페이지가 소실**된다(UX-2). 두 문제는 뿌리가 같다: 필터 상태의 **단일 소유처가 없다.**
> **목표**: 필터 상태를 **URL(searchParams) 단일 소유**로 옮겨 두 문제를 동시에 해소한다 — 死코드/이중화 제거(C-S2 해소)와 필터의 URL 지속(UX-2 해소)을 한 번에.
> **스코프**: 기존 각 페이지의 **필터 차원을 그대로 보존**한다(characters: 이름 검색·House / spells: 검색·category / potions: 검색·difficulty / movies: 검색). 필터 변경 시 페이지 리셋 등 기존 filterStore가 상정한 규칙을 계승한다.
> **비목표**: 전역 검색·신규 정렬 차원의 **도입은 하지 않는다**(향후 후보로 유지). 새 필터 UI·필터 항목 추가도 이번 스코프가 아니다 — 소유처 이전이지 기능 확장이 아니다. 필터 상태를 어떤 기제(URL 직접 vs 라이브러리)로 지속시킬지의 HOW는 architect가 정한다.

- **AC-11**: 목록 페이지(`/characters`, `/spells`, `/potions`, `/movies`)에서 검색어·필터 선택·현재 페이지가 **URL 쿼리 파라미터**로 표현된다. 그 URL을 새로고침하거나 북마크·타인 공유로 다시 열면, 동일한 검색어·필터·페이지가 적용된 동일한 목록 결과가 복원된다. → UX-2 해소.
  - _검증 노트_: URL↔상태 양방향 반영과 복원 **배선의 존재**는 정적으로 확인 가능하나, "새로고침·공유 링크 진입 후 시각적으로 동일 결과가 뜨는가"의 최종 동치는 헤드리스 정적 검증 불가 → **gate3(휴먼 수용) 대상**(D-2의 AC-8 새로고침 지속 검증을 gate3에 위임한 선례 계승).
- **AC-12**: 각 목록 페이지의 **지속되는(persistent) 필터·검색·페이지 상태의 소유처가 URL로 단일화**되어, 페이지 컴포넌트가 이 상태를 URL과 경쟁하는 별도 지속 상태로 **이중 보유하지 않는다**. 소비자 0의 `lib/stores/filterStore.ts`(死코드)가 저장소에서 제거된다. 이 과정에서 각 페이지의 **기존 필터 차원이 그대로 보존**된다 — characters=이름 검색·House(4하우스+All)·page / spells=검색·category·page / potions=검색·difficulty·page / movies=검색·page. → C-S2 해소.
  - _검증 노트_: `filterStore.ts` 부재와 페이지의 필터 상태 이중 보유 부재, 필터 차원 보존은 정적(코드 대조)으로 확인 가능. (검색 입력의 커밋 전 순간값을 view 상태로 로컬에 두는지 등 지속 경계의 HOW는 architect/SDD 몫 — AC는 "지속 상태의 단일 소유"만 요구.)
- **AC-13**: 필터 또는 검색어를 변경하면 현재 페이지가 **1로 리셋**된다. 기본값 상태(검색어 없음·필터 미선택·1페이지)에서는 해당 파라미터가 URL에 **부착되지 않는다**(깨끗한 URL: 기본값은 파라미터 없는 경로). → 기존 filterStore 페이지 리셋 규칙 계승.
  - _검증 노트_: 리셋·기본값 생략 규칙의 배선 존재는 정적으로 확인 가능하나, "변경 상호작용 후 실제 URL 문자열이 기대대로 바뀌는가"의 관찰은 **gate3(휴먼 스모크) 대상**.

### 로컬 즐겨찾기 (D-5 재진입, 2026-07-09)

> **WHY**: 사용자가 둘러보다가 다시 보고 싶은 캐릭터·주문·마법약·영화·책을 앱 안에서 임시로 모아둘 표면이 없다. 로그인·서버 쓰기 없이도, 같은 브라우저에서 관심 항목을 빠르게 재방문할 수 있어야 한다.
> **목표**: 5종 엔티티 모두를 로컬 브라우저 저장소에 즐겨찾기로 저장하고, `/favorites`에서 모아본다.
> **스코프**: localStorage 기반 단일 브라우저 저장. 목록 카드와 상세 페이지에서 토글 가능. 즐겨찾기 목록은 저장 당시의 최소 표시 메타데이터(제목·보조문구·이미지·상세 링크)를 사용한다.
> **비목표**: 로그인 동기화, 서버 저장, 계정 간 공유, API 재조회 기반 최신화, 정렬/필터 고도화.

- **AC-14**: 캐릭터·주문·마법약·영화·책의 목록 카드와 상세 페이지에 즐겨찾기 토글이 있고, 클릭 시 같은 브라우저에서 저장/해제 상태가 즉시 반영된다.
- **AC-15**: `/favorites` 라우트가 존재하며 저장된 즐겨찾기를 엔티티 구분과 함께 표시한다. 각 항목은 원래 상세 페이지로 이동할 수 있고, 목록에서 바로 해제할 수 있다.
- **AC-16**: 즐겨찾기 상태는 새로고침 후에도 유지된다(localStorage). 저장 항목이 없을 때는 빈 상태를 명확히 렌더한다.

### 다국어 i18n — ko + en (2026-07-10 활성 목표 승격, 첫 product feature 파이프라인 완주)

> spec가 아래 WHY를 **비목표에서 활성 목표로 승격**(State 재진입, 근거는 session에 흔적). requirement가 이어서 AC-*로 조인다. 근거·정합: Domain 유비쿼터스 언어(House·Entity 등 도메인 어휘의 단일 출처), R-5(필터 어휘 API 종속).
> **WHY(문제·배경)**: 앱 UI 추(chrome — 내비게이션·필터 라벨·상태 문구·버튼·빈/에러 상태 등)와 도메인 어휘(House·Entity 명칭 등)가 영어로만 노출된다. 한국어 사용자는 세계관 몰입(G-3)과 탐색 도달(G-2)에서 언어 장벽을 만난다. 이 앱은 그간 영문 원본을 비목표 방어선으로 삼아왔으나, 한국어권 팬 방문자 비중을 고려하면 **UI 추와 고정 도메인 어휘만이라도** 모국어로 열람할 표면이 필요하다. 동시에 이 feature는 거버넌스 하네스가 **처음부터 한 바퀴 완주하는 첫 product feature**다(직전까지는 역복원 부채·재진입이었음 — session "다음 세션 인계"의 신규 feature 발굴).
> **목표**:
> - i18n-G1. **en(기본) + ko** 2개 언어를 지원한다.
> - i18n-G2. UI 추(chrome) 전면을 번역한다 — 내비게이션·필터/정렬 라벨·검색 플레이스홀더·로딩/에러/빈 상태 문구·버튼·공통 레이아웃 텍스트.
> - i18n-G3. 고정 **도메인 어휘**(House 4종·Entity 5종 등)를 사전 매핑으로 ko 표기한다. 이 ko 매핑의 단일 출처는 `docs/state/Domain.md`(유비쿼터스 언어)와 정합해야 한다.
> - i18n-G4. 라우팅을 경로 프리픽스 `/[locale]/`로 옮긴다 — 모든 라우트가 `[locale]` 하위로 이동, 언어가 URL로 표현·공유된다.
> - i18n-G5. **en 기본**, 첫 방문 시 `Accept-Language`로 감지, 선택은 쿠키로 기억한다.
> **스코프**: 번역 대상은 **UI 추 전면 + 고정 도메인 어휘 사전**이다. API가 내려주는 **가변 콘텐츠 설명**(인물 전기·주문/마법약 effect·챕터 summary 등 canon 서술문)은 **영문 원본을 유지**한다(번역 스코프 밖 — 위 비목표에서 이관된 사실). 라이브러리 방향은 **next-intl**을 잠정 지목하되, 최종 라이브러리·기제 확정은 architect의 HOW/ADR 몫이다(WHY 단계는 방향만, 확정은 decision-queue로 → i18n 라이브러리 항목).
> **비목표**: (1) API 가변 콘텐츠(전기·설명·summary) 번역, (2) 3번째 언어의 **실제 구현**(en+ko만 — 확장 여지는 카탈로그 구조가 열어두되 구현 안 함), (3) RTL(우→좌) 레이아웃.

> requirement가 i18n-G1~G5·스코프를 아래 AC-17~AC-22로 조였다(2026-07-10). 정적 오라클은 **AC-7**(tsc·lint·build)이 전역으로 커버 — i18n 도입 후에도 AC-7이 그대로 적용되므로 중복 AC를 신설하지 않는다.

- **AC-17** (i18n-G1 · en+ko 2언어 + 스위처): 앱이 **en(기본)과 ko** 두 로케일을 지원한다. UI에 언어 스위처 컨트롤이 있고, 활성 로케일을 en↔ko로 전환하면 UI 추(chrome)가 대상 로케일 문자열로 다시 렌더된다. 두 로케일 각각의 메시지 카탈로그가 저장소에 존재하고, en에 있는 chrome 키가 ko에도 빠짐없이 존재한다(키 대칭).
  - _검증 노트_: 두 카탈로그의 존재·키 대칭과 스위처 배선의 존재는 정적(코드·파일 대조)으로 확인 가능. "스위처 클릭 후 화면이 시각적으로 대상 언어로 바뀌는가"의 최종 동치는 헤드리스 정적 검증 불가 → **gate3(휴먼 수용) 대상**(D-2 AC-8·D-1 AC-11 선례 계승).
- **AC-18** (i18n-G2 · UI 추 전면 번역): UI 추 전면이 활성 로케일 문자열로 렌더된다 — 내비게이션, 필터/정렬 라벨, 검색 플레이스홀더, 로딩/에러/빈 상태 문구, 버튼, 공통 레이아웃 텍스트. 아울러 `<html lang>` 속성이 활성 로케일을 반영하고, 페이지 metadata(title·description)가 로케일별로 렌더된다. 위 chrome 표면에 활성 로케일 카탈로그를 우회하는 하드코딩 영문 문자열이 남지 않는다.
  - _검증 노트_: 카탈로그 키 존재와 각 chrome 표면이 그 키를 소비하는 배선, `<html lang>`·metadata의 로케일 연동은 정적으로 확인 가능. "ko 로케일에서 모든 chrome 표면이 빠짐없이 한국어로 뜨는가"(누락 문자열 없음)의 시각적 완전성은 **gate3(휴먼 수용) 대상**.
- **AC-19** (i18n-G3 · 고정 도메인 어휘 ko 매핑): 고정 도메인 어휘 — House 4종(Gryffindor·Slytherin·Ravenclaw·Hufflepuff)·Entity 5종(Character·Spell·Potion·Movie·Book)·Chapter — 가 ko 로케일에서 사전 매핑으로 한국어 표기된다. 이 ko 매핑은 **`docs/state/Domain.md` 유비쿼터스 언어 표의 ko 표기 표준(단일 출처)과 정합**한다. API 종속 필터 어휘(Spell `category`·Potion `difficulty` 등 R-5류)의 **원문 키는 영문으로 유지**되며(도메인이 필터 키를 재명명하지 않음), ko 화면에 이들의 한국어 라벨을 노출하더라도 그것은 카탈로그 표시 라벨일 뿐 원문 키 자체를 바꾸지 않는다.
  - _검증 노트_: 카탈로그의 도메인 어휘 ko 값이 Domain.md ko 표기 표준과 문자 일치하는지, 필터 원문 키가 영문 유지인지는 정적(문서↔코드 대조)으로 확인 가능. → i18n-G3 "ko 매핑 단일 출처=Domain.md" 요구 충족.
- **AC-20** (i18n-G4 · `/[locale]/` 프리픽스 라우팅): 모든 라우트가 `/[locale]/` 프리픽스 하위로 이동해, **활성 언어가 URL 경로로 표현**된다. 그 로케일 URL을 북마크·타인 공유로 다시 열면 동일한 언어가 복원된다. (기본 언어(en)에 프리픽스를 always 붙일지 as-needed로 생략할지의 **표기 정책 HOW는 architect 미결 D-9** — 이 AC는 "언어가 URL 경로로 표현되고 공유 링크로 복원된다"까지만 요구하고 always/as-needed 표기 정책은 요구하지 않는다.)
  - _검증 노트_: 라우트가 `[locale]` 세그먼트 하위로 구성되고 URL↔로케일 배선이 존재함은 정적으로 확인 가능. "공유 링크 진입 후 실제로 해당 언어로 화면이 복원되는가"의 시각적 최종 동치는 **gate3(휴먼 수용) 대상**(D-1 AC-11 URL 복원 선례 계승).
- **AC-21** (i18n-G5 · en 기본 + Accept-Language 감지 + 쿠키 지속): en이 기본 로케일이다. 첫 방문(지속 선택 쿠키 부재) 시 `Accept-Language` 헤더로 초기 로케일을 감지하고, 이후 사용자의 언어 선택은 **쿠키로 지속**되어 새로고침·재방문에 유지된다(쿠키가 있으면 감지보다 쿠키 선택이 우선).
  - _검증 노트_: Accept-Language 감지와 쿠키 read/write·우선순위 배선의 존재는 정적으로 확인 가능하나, "감지·쿠키 지속의 결과가 새로고침·재방문에서 시각적으로 동일 언어로 유지되는가"의 최종 동치는 **gate3(휴먼 수용) 대상**(D-2 AC-8 새로고침 지속 선례 계승).
- **AC-22** (스코프 가드 · API 가변 콘텐츠 영문 유지): API가 내려주는 가변 canon 서술문 — 인물 전기(biography 등)·Spell/Potion `effect`·Chapter `summary` 등 — 은 **ko 로케일에서도 영문 원본을 유지**한다(번역 스코프 밖). i18n 도입이 이 콘텐츠를 로케일에 따라 억지 번역하지 않음을 회귀 방지로 명문화한다.
  - _검증 노트_: 해당 콘텐츠 필드가 번역 계층(카탈로그 조회)을 거치지 않고 API 원본을 그대로 렌더함은 정적(코드 경로 대조)으로 확인 가능. "ko 화면에서 이들 서술문이 영문으로 보이는가"의 시각 확인은 **gate3(휴먼 수용)** 로 보조.
